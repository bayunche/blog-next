# 页面样式与功能优化方案（2026-02-27）

## 1. 现状结论
- 当前核心功能链路可用：登录、文章 CRUD、评论接口、音乐接口、主要页面可达。
- 已完成关键修复：
  - 后台文章编辑页音乐搜索链路修复（`/music/search` + 前端解析修复）。
  - 后台文章更新分类/标签字段修复（`categories/tags`）。
- 仍有可优化空间：视觉一致性、交互稳定性、数据真实性、构建期告警。

## 2. 目标
- 样式目标：统一视觉语言，减少“随机外部资源”导致的不稳定与风格漂移。
- 功能目标：减少“看起来有功能但数据是假值”的情况，提升后台实际可运营性。
- 工程目标：降低构建告警，补齐自动化回归和类型约束。

## 3. 优先级方案

### P0（本周，建议立即做）
1. 后台仪表盘改为真实数据
- 问题：`/admin` 页面统计为硬编码值（文章数、评论数、访问量）。
- 方案：新增统计接口（文章总数、评论总数、浏览量汇总），前端实时请求渲染。
- 价值：管理端从“展示页”变成“可运营页”。
- 状态：已完成（`/monitor/summary` + 前端接入）。

2. 文章详情评论数改为真实值
- 问题：文章头部显示“0 评论”为硬编码。
- 方案：改为读取接口返回的评论数量（或 remark42 统计接口/本地缓存统计）。
- 价值：避免误导用户，提升信息可信度。
- 状态：已完成（文章详情头部改为实时评论数量）。

3. 评论区增加“服务不可用”降级提示
- 问题：Remark42 不可达时用户只能看到空白评论区域。
- 方案：脚本加载失败时显示明确提示（如“评论服务暂时不可用，请稍后重试”）。
- 价值：降低用户困惑和误报 bug 的概率。
- 状态：已完成（脚本加载失败时显示降级提示）。

4. 修复构建期 API 依赖告警
- 现象：构建期偶发 `ENOTFOUND server`（归档静态生成阶段）。
- 方案：构建时避免强依赖容器内服务名；统一 fallback 与构建时 mock 逻辑。
- 价值：提升 CI/CD 稳定性，减少“构建成功但有隐患”。
- 状态：已完成（`/archives` 改为动态渲染，构建阶段不再请求 `server`）。

5. 音乐播放链路稳定性
- 问题：播放器存在外链 URL 回退，受版权/跨域影响时会出现“可点击但无法播放”。
- 方案：前端统一使用 `/api/music/proxy/:id`；后端 `/music/url` 只返回代理地址；`/music/proxy` 优先使用 `song/url/v1` 解析可播放源并代理流式返回。
- 价值：减少外链失效导致的播放故障，保障文章内音乐与全局播放器行为一致。
- 状态：已完成（已通过 29/29 自动化回归，含代理流播放专项校验）。

### P1（1-2 周）
1. 视觉资源去外部依赖化
- 问题：多个页面背景图依赖第三方随机图 API，可能慢、失败、风格不一致。
- 方案：本地化一组高质量背景资源 + 可控随机策略；外部源作为兜底而非主路径。
- 价值：页面稳定性和品牌一致性显著提升。
- 状态：已完成（登录页/后台页/文章卡片/懒加载图采用本地优先策略；文章详情页使用统一背景层，标题区滚动到正文区保持同图；关于页头像改为本地资源）。

2. 动效与滚动效果参数统一
- 问题：Hero、卡片、播放器等动效节奏不完全统一，体验略“散”。
- 方案：抽离 motion tokens（时长、缓动、位移）并在全局复用。
- 价值：整体观感更“整站化”，减少局部突兀。
- 状态：已完成（已新增全局 motion tokens，并接入 Hero、全局 Background、Navbar、ArticleCard、MusicPlayer、TableOfContents、FloatingToolbar、AdminLayout 等高频交互区域）。

3. 后台文章编辑体验增强
- 方向：
  - 分类/标签自动补全（从已有数据候选）。
  - 音乐搜索结果缓存与分页。
  - 上传失败重试与错误明细。
- 价值：降低运营编辑成本。
- 状态：已完成（编辑器已接入分类/标签候选、音乐搜索服务端分页 + 前端缓存、封面上传失败重试与错误明细提示）。

4. 音乐配置后台化（Cookie + 默认歌单）
- 问题：版权歌曲是否可播依赖登录态，且默认播放列表不可运营配置。
- 方案：后台增加“网易云播放配置”管理区（手动 Cookie + 二维码登录 + 默认歌单 ID）；播放器首次加载读取 `/music/playlist/default`。
- 价值：运营可直接维护可播性与默认歌单，无需改代码重发版。
- 状态：已完成（并通过 `npm run test:music:smoke` 抽样 8/8 可播校验）。

### P2（2-4 周）
1. 可观测性与回归体系
- 方案：
  - 增加 E2E 自动化（登录、文章编辑、评论可用性、音乐播放链路）。
  - 增加关键接口健康检查（启动后自动跑 smoke test）。
- 价值：减少回归故障，支持持续迭代。

2. 设计系统化
- 方案：抽离颜色/圆角/阴影/间距/字体 token，建立组件级规范（按钮、卡片、表单、弹窗）。
- 价值：后续新增页面成本更低，风格更一致。

## 4. 建议验收指标（可量化）
- 功能稳定：
  - 核心回归脚本通过率保持 100%。
  - 评论与音乐接口 5xx 比例 < 0.5%。
- 性能体验：
  - 首屏可交互时间（TTI）下降 15%。
  - 外部图片请求失败率下降 80%。
- 运营效率：
  - 文章发布/编辑平均耗时下降 30%。

## 5. 建议落地顺序
1. 先做 P0 的 5 项（真实性、可用性、构建稳定、音乐播放链路稳定性）。
2. 再做 P1 的视觉统一和编辑体验。
3. 最后用 P2 完成自动化与设计系统化。
